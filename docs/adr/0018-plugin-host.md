# ADR-0018: プラグインのホスト（v0 の検査ルールと v1 の TypeScript プラグイン）

- 状態: 提案
- 日付: 2026-10-16

## 背景

ADR-0004 で、プラグインを 3 段階（v0：YAML の検査ルール、v1：TypeScript、v2：WASM Component）で入れること、
契約を plugin-sdk（MIT）に置くこと、権限をマニフェストで宣言させてホストが強制することを決めた。
plugin-sdk には、マニフェスト・レジストリの索引・`TextEdit`・`Diagnostic` の型がすでにある（`apiVersion` は `"0"`）。

一方、本体にはプラグインを読み込む・動かす仕組み（ホスト）が無い。スプリント 5（`0.1.0-alpha.5`）で、v0 と v1 のホストを入れる（メンテナの判断。利用者からの要望より先に入れる）。
決めることは次のとおり。

- プラグインをどこから読み込むか（静的配信のまま、C-4）
- v0 の検査ルールの書き方と、どこで解釈するか（ブラウザと CI で同じ結果にする、ADR-0004）
- v1 のプラグインをどこで動かし、権限をどう強制するか（C-2：利用者のデータを外部に送らない）
- プラグインからの変更を、テキストが唯一の正本（ADR-0001）という原則にどう合わせるか
- 契約のうち、plugin-sdk に新しく足すもの

## 決定

### 1. 読み込む場所

- alpha.5 では、**開いたフォルダの `.modelith/plugins/<名前>/manifest.json`** からだけ読み込む（ワークスペースのプラグイン）。
  モデルと一緒にリポジトリに置けば、チームの全員と CI が同じルールを使える。
- CLI は `modelith check <ファイル…> --plugins <フォルダ>` で同じ置き場所を読む。
- フォルダを開けないブラウザ（F-FILE-10）では、プラグインを読み込まない。そのことを画面に示す。
- レジストリ（`plugin-registry`）からの追加と、ブラウザへの登録（フォルダをまたいで使う）は、0.1.0 の後に決める。

### 2. v0：検査ルール（YAML）

- マニフェストの `contributes.rules` に、ルールの YAML ファイルを並べる。**コアだけ**（Rust の `modelith-core`）が解釈する。
  ブラウザ（Worker 内の wasm）と CLI が同じコードで動くので、結果は同じになる（ADR-0002 で避けた「ブラウザでは通るのに CI で落ちる」を防ぐ）。
- ルールは、今のモデル（`Model` の要素・関係）で判定できることに限って始める。

  ```yaml
  rules:
    - id: req-has-satisfier          # プラグインの中で一意
      severity: warning              # error / warning / information
      message: "要求「{name}」を満たす部品がありません"
      match:                         # どの要素に当てるか（すべて満たすもの）
        kind: requirement def        # 要素の種類（1 つか並び）
        phase: SystemRequirements    # 任意。工程（@Phase）
        name: "^[A-Z]"               # 任意。名前の正規表現
      require:                       # 満たすべき条件（すべて）
        incoming: satisfy            # この種類の関係を、ほかの要素から 1 本以上受ける
  ```

  `require` の語彙は、`name`（正規表現）・`phase`（工程を持つ）・`incoming` / `outgoing`（関係の種類）・`ports`（数の下限と上限）から始め、
  `not` で否定できる。語彙を足すのは互換を保つ追加として扱う（plugin-sdk の互換性ルール）。
- 未知のキー・対応しない `apiVersion`・正規表現の誤りは、黙って捨てない。どのファイルの何行目が悪いかを、問題一覧とプラグインの一覧に示す（F-EDIT-8 と同じ考え方）。
- 検査の結果は、問題一覧に、ルールの ID とプラグインの名前を添えて出す。CLI は結果を出し、`error` が 1 件でもあれば 0 以外で終わる。
- ルールの形（`RuleSet`）は plugin-sdk に Rust の型として置き、JSON Schema を生成する（YAML のエディタ補完にも使える）。

### 3. v1：TypeScript のプラグイン

- **動かす場所**：プラグインごとに、サンドボックス化した iframe（`sandbox="allow-scripts"`、独自のオリジンを持たない）の中の Worker で動かす。
  - iframe には自前の CSP を付ける。`network` を宣言していなければ `connect-src 'none'` にし、外部と通信できなくする。
  - 独自のオリジンを持たないので、アプリの下書き・開いているフォルダ・`localStorage` には触れられない。
  - ADR-0004 は「Web Worker」とだけ書いていた。Worker だけでは、アプリと同じオリジンで動き、通信や保存を止められないため、iframe で囲む（ADR-0004 の具体化）。
  - スプリントの最初に、ブラウザ（Chrome・Edge・Safari・Firefox）で iframe の中に Worker を作れること、CSP が効くことを確かめる。作れないブラウザでは、iframe の中で直接動かす。
- **やり取り**：ホストとプラグインは `postMessage`（`MessageChannel`）で、版つきのメッセージをやり取りする。メッセージの型は plugin-sdk に置く。

  | ホスト → プラグイン | プラグイン → ホスト |
  | --- | --- |
  | `activate { apiVersion }` | `ready` |
  | `didChange { version, text, model }`（`model:read` のとき） | `diagnostics { version, items }`（`model:read` のとき） |
  | `runCommand { id }` | `proposeEdits { version, edits }`（`edits:propose` のとき） |
  | `import { importer, fileName, bytes }` | `imported { text }` |
  | `export { exporter, view }` | `exported { fileName, mediaType, bytes }` |
  | `storageResult { … }` | `storage { get / set }`（`storage` のとき） |

- **権限**：宣言していない権限のメッセージは、ホストが捨てて、プラグインの一覧に知らせる。`storage` は、ホストがプラグインごとに分けた保存場所を貸す（プラグインはブラウザの保存場所に直接触れない）。
- **alpha.5 で使える働き**：コマンド（メニューから実行）・取り込み・書き出し・`model:read` による検査。
  ビュー（宣言的な描画指定）とパレットは、図の描画を Rust に移した後（ADR-0017 の段階 2 と合わせて）に決める。

### 4. テキストの編集（ADR-0001 との両立）

- プラグインからの変更は、すべて `TextEdit`（plugin-sdk、行・列）の変更案として受ける。ホストは適用する前に次を確かめる。
  - `version` が今のテキストの版と同じか。違えば適用せず、「テキストが変わったため、プラグインの変更をやめました」と知らせる（ADR-0016 と同じ）
  - 範囲がテキストの中にあり、重なっていないか
- 適用した変更は、1 回の「元に戻す」で取り消せる。適用した後は、ふつうの編集と同じく解析し直す。
- 取り込みの結果（`imported`）は、新しい無題のファイルとして開く。既存のファイルを黙って書き換えない（C-6）。

### 5. 信頼と許可

- v0 のルールはコードを含まないので、読み込んだらそのまま使う。
- v1 のプラグインは、**初めて動かす前に、利用者に許可を求める**。名前・作者・版・宣言した権限を、ADR-0014 の言葉で示す。
  `network` を宣言しているときは、「このプラグインは、あなたのモデルを外部に送れます」と明示する（C-2 の例外を、利用者が選んだときだけにする）。
- 許可は、プラグインの ID・版・ファイルのハッシュの組ごとにブラウザに記憶する。版かファイルが変わったら、もう一度尋ねる。
- プラグインの一覧（画面）で、読み込んだプラグイン・状態・誤り・許可を確かめ、止められる。

### 6. 契約（plugin-sdk に足すもの）

| 型 | 内容 |
| --- | --- |
| `RuleSet` / `Rule` | v0 のルールの形（JSON Schema も生成） |
| `HostMessage` / `PluginMessage` | v1 のやり取りのメッセージ |
| `ModelSnapshot` | プラグインに渡すモデル（要素・関係・問題）。安定するまで互換を約束しない（`apiVersion` `"0"` の間） |

本体側では型を定義しない（CLAUDE.md）。plugin-sdk に足す PR を先に出し、本体はその版に依存する。

### 7. 0.2.0 の FMEA プラグインを見据えて

0.2.0 で、FMEA（故障モード影響解析）をモデルと結びつけるプラグインを作る（メンテナの要望）。alpha.5 のホストは、これを妨げない形にする。
FMEA のプラグインには、alpha.5 の範囲を超える次のものが要る。どれも 0.2.0 の前に、別の ADR で決める。

| 要るもの | 理由 | alpha.5 での扱い |
| --- | --- | --- |
| メタデータの属性値（重大度・発生度・検出度など）と、接続・doc を含むモデル | 故障モードの評価と、構造をたどった影響の伝播 | `ModelSnapshot` は互換を約束しない（`apiVersion` `"0"`）ので、後から足せる |
| 表のビュー（FMEA の表） | FMEA は表で見て、表で直すのが普通 | ビューは入れない（3.）。宣言的な描画指定に表を含められる形にしておく |
| プラグインが配るライブラリ（FMEA の定義の SysML ファイル） | 故障モードを書く語彙をそろえる | 入れない。`contributes` に任意の項目として足せる |
| 値の比較ができる検査ルール（例：RPN が閾値以上なのに対策が無い） | v0 で組織の基準を CI で回す | `require` の語彙の追加（互換を保つ追加）で足せる |
| 表の列を、プラグインの設定（YAML）で決める | FMEA の列（項目）は会社ごとに違う | ビューの宣言に、列の定義を任意の項目として足せる形にしておく |
| ポート・属性まで結びつけられるモデル | 故障は部品だけでなく、つなぎ口（ポート）や属性にも起きる | 今のモデルは部品とポートまで。属性は、0.1.0 の後のモデル構築の作り直し（ADR-0016）で扱う |

参考にした考え方（MBSE Solutions「How to Model Your FMEA With SysML」、2016）：
FMEA の項目をモデルの要素として置き、trace の関係で設計の要素（部品・機能・インターフェース・振る舞い・ポート・属性）に結びつける。
1 つの項目が FMEA の表の 1 行になり、対策（コントロール）も項目に結びつけた要素として持つ。
SysML v2 のテキストでは、項目を定義（`item def`）として、結びつきを名前を付けた関係（`#trace dependency`）として書ける。

もう 1 つの参考（Hecht・Baum・Betser「Automated Failure Modes and Effects Analysis using SysML for Industrial Computer Network Reliability and Cybersecurity」、IM 2019）は、FMEA を自動で作る。
部品の型ごとに、入口（sink）と出口（source）の故障の口を持たせ、型の中で故障が伝わる・別の故障に変わる道筋を定義する。
部品どうしの接続（関連ブロック）にも、伝わり方と変わり方を定義する。そのうえで、故障モードと原因の組ごとに、末端の影響までのすべての伝播経路を数え上げ、経路ごとに長さと、最初に検出・緩和・防護できる位置を求める。
結果は 5 つの表（全 FMEA・故障モードと影響の集計・システムの影響・診断の行列・伝播の詳細）として Excel に書き出す。攻撃者を部品の 1 つとして置けば、サイバー攻撃の経路も同じ方法で分析できる。
これを Modelith で行うには、上の表に加えて次のものが要る。

- 入れ子のポート（故障の口の中の故障モード）と、型の中・接続の定義（`connection def`）の中の `connect` を含むモデル
- 経路の数え上げは、要素数に対して大きく増える（論文の小さな例でも 1110 行）。循環の扱いと上限を、プラグインの側で決める
- 複数のシートを持つ表計算ファイルへの書き出し（プラグインの書き出しで扱える）

0.2.0 では、設計の FMEA（dFMEA）から始める。使い方の FMEA（uFMEA）と工程の FMEA（pFMEA）は、アクティビティ図の列（スイムレーン）を扱えるようになってから入れる。

## 進める順序

| 手順 | 内容 |
| --- | --- |
| A | plugin-sdk に `RuleSet` と、v1 のメッセージの型を足す |
| B | コアに検査ルールの解釈を足し、CLI の `check` を作る |
| C | 画面：フォルダからの読み込み・プラグインの一覧・問題一覧への表示 |
| D | v1：iframe と Worker の確認、ホスト、許可、コマンド・取り込み・書き出し |

手順ごとに PR を分け、要求に `verify` を結ぶ。

## 結果

- 組織ごとの検査ルールを、ブラウザと CI で同じ結果で回せる（ADR-0004 の v0 の目的）。
- v1 のプラグインは、宣言した権限の外に出られない。外部に送れるのは、利用者が許可した `network` のプラグインだけになる。
- プラグインの変更もテキストの編集なので、元に戻す・差分・競合の扱いは、今の仕組みのまま使える。
- 静的配信のまま（C-4）。サーバは要らない。
- plugin-sdk のメッセージは、ADR-0017（ほかのウェブアプリとの連携）の埋め込みのメッセージと同じ考え方になる。
