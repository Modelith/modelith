# ADR-0015: Rust パーサの作り方と、暫定コアからの差し替え方

- 状態: 採用（2026-10-15 改訂：Worker へ移す時期を alpha.4 に変更。2026-10-19 改訂：段階 B・C の時期を、文法への対応の計画に合わせた）
- 日付: 2026-10-15

## 背景

スプリント 3（`0.1.0-alpha.3`）で、暫定の TS パーサ（`web/src/core/parser.ts`、ADR-0009）を Rust のパーサに差し替える（[リリース計画](../development/release-plan.md)）。
大枠は決まっている。

- コアは Rust の `modelith-core`。ブラウザでは Web Worker 内の wasm で動かす（ADR-0002・ADR-0003）。
- パーサは rust-analyzer と同じ方式で作る。ロスレスな CST を作り、エラーがあっても続きを読む（ADR-0002）。
- 正しさの基準は「SysML v2 仕様 > モック」（ADR-0013）。仕様のケースは `spec.test.ts`、モックと同じ振る舞いの範囲はゴールデンで確かめる。

決まっていないのは、次の 4 点である。

1. どの文法から、どの順に対応するか
2. Rust のパーサが、ゴールデンと仕様のケースを満たすことを、どう確かめるか
3. 暫定コアのどこまでを、alpha.3 で差し替えるか
4. 今は同期で呼んでいる解析を、いつ・どう Worker の非同期に移すか

## 決定

### 1. パーサの構成

`modelith-core` に、次の層を置く。上の層は下の層だけに依存する。

| 層 | 役割 |
| --- | --- |
| `lexer` | テキストを、空白・コメントを含むすべてのトークンに分ける。手書きで、正規表現を使わない |
| `parser` | 再帰下降でトークンを読み、木を組む「イベント」を出す。木そのものは作らない（rust-analyzer と同じ） |
| `syntax` | イベントから `rowan` のロスレスな木（CST）を作る。木の文字列は入力と 1 文字も違わない |
| `project` | CST から、暫定コアと同じ形の解析結果（`ParseResult`）を作る。alpha.4 でモデル構築に置き換える |

- **木の節の名前は、SysML v2 の BNF の規則名にそろえる**（`PartDefinition`、`OwnedSubsetting` など）。仕様との対応表とテストを、規則名で結び付けるためである。
  BNF のファイルそのものはリポジトリに入れない。規則名と章番号だけを引用する。
- **エラーに強くする。** 読めない部分は `ERROR` の節に入れ、`;`・`}`・宣言の頭のキーワードまで読み飛ばして続きを読む。どんな入力でも panic しない。
- **パーサ生成器（pest・lalrpop・tree-sitter など）は使わない。** エラーからの回復、ロスレスな木、wasm の大きさの 3 点を、手書きのほうが制御しやすいためである。
- 外部のクレートは `rowan` だけを本体の依存にする。テストでは、木の形を比べるために `expect-test` を使う。
- 位置は、コアの中ではバイトオフセットで持つ。UI との境界で UTF-16 に直す（`LineIndex`、ADR-0003）。
- 部分的な再解析は、alpha.3 では作らない（YAGNI）。1 万行のモデルを全体で解析する時間を計り、Worker の中で 50 ms を超えたら作る。

### 2. 文法に対応する順序

| 段階 | 対象 | 時期 |
| --- | --- | --- |
| A | 暫定コアが読んでいる範囲のすべて。package、`import`・`alias`、定義と使用（暫定コアの `DEF_KINDS`・`USAGE_KINDS`）、名前（基本名・引用名・短い名前）、型付けと特殊化（`:`・`:>`・`:>>`・`::>` とそのキーワード）、多重度、`= 値`、`doc`・`comment`、メタデータ（`#M` と `@M { … }`）、関係（満たす・検証する・扱う・流れ・接続・メッセージ・依存・遷移）、`expose`・`filter`・`render`、列挙値、向きの付いたパラメータ | alpha.3 |
| B | 式の文法（8.2.2 の Expressions）。段階 A では、式を括弧の釣り合いだけで区切る「まだ読まない式」の節として持つ | 0.3.0 以降（式の評価・単位とあわせて） |
| C | アクション・状態・ケースの本体の細部と、関係の残り。[対応表](../reference/sysml-conformance.md) の × と △ を、[リリース計画](../development/release-plan.md) の「SysML v2 の文法への対応」の順に埋める。パッケージやファイルをまたぐ名前の解決（`import`・`alias`・修飾名）は 0.2.0 | alpha.7〜alpha.9 |

- どの段階でも、**読めない文を黙って捨てない**（F-EDIT-8）。予約語で始まるのに読み方の無い文は、今と同じく「まだ扱えない構文」として返す。
- 段階を進めるたびに、対応表を更新する。

### 3. 確かめ方

**同じテストを、TS と Rust の両方のパーサで動かす。** テストを 2 つの言語に書き分けない。

- `golden.test.ts` と `spec.test.ts` は、パーサを引数に取る形にし、暫定コアと Rust（wasm）の両方で実行する。
  両方を通ることが、差し替えの条件になる。
- Rust の wasm は、テストのために Node 向けにもビルドする。`scripts/check.sh` は、web のテストの前に wasm をビルドする。
- ゴールデンと比べるとき、構文エラー（`errors`）は、問題一覧と同じく文言を比べず、位置だけを比べる（ADR-0014）。
- alpha.7 以降に足す文法のケースは、Rust のコアだけで確かめる。暫定の TS コアは alpha.6 の範囲で止め、beta.1 で削除する。
- Rust の中では、次を単体テストにする。
  - 字句と木の形（`expect-test` で、木を文字列にして比べる）
  - ロスレス：どの入力でも、木の文字列が入力と一致する
  - エラーへの強さ：ゴールデンのケースとサンプルを、あらゆる位置で途中まで切った入力でも、panic せず、ロスレスである

### 4. 差し替える範囲と、呼び出し方

- **alpha.3 で差し替えるのはパーサだけ**とする。モデル構築（`model.ts`・`views.ts`）とテキスト編集（`text-ops.ts`）は alpha.4 で差し替える。
- Rust は、暫定コアと同じ形の `ParseResult` を返す。要素どうしの参照（親・子・持ち主）は番号で渡し、TS の境界で今のオブジェクトの参照に戻す。
  これで、モデル構築と UI を変えずにパーサだけを入れ替えられる。
- **alpha.3 では、Rust のパーサを画面と同じスレッドで、同期で呼ぶ。** 起動時に wasm を読み込んでから、最初の描画をする。
  今の呼び出し方（テキストを変えたら、その場で解析し直す）は変えない。
- **Worker に移すのは alpha.4 とし、モデル構築・テキスト編集と一緒に移す**（ADR-0003・Q-1）。
  そのとき、図の操作は「コアにテキスト編集を求める」形（LSP のコードアクションと同じ）にし、解析結果を待つ間の操作も正しい位置を書き換えるようにする。
- 暫定の TS パーサは、比べるテストのために beta.1 まで残す。画面からは使わない（ADR-0009 の削除の目標は変えない）。
- ビルドには `wasm-bindgen-cli` を使う。版は `wasm-bindgen` クレートの版と一致させ、セッション開始のフックと CI で用意する。

### 4 の改訂の理由（2026-10-15）

当初は alpha.3 で解析を Worker に移すと決めたが、実装して計ると、次のことがわかった。

| 公開サンプルをつないだモデル（Node で計測） | 暫定の TS | Rust（wasm の中） | Rust（JSON を受け取り、オブジェクトに戻すまで） |
| --- | --- | --- | --- |
| 280 行 | 0.9 ms | — | 2.0 ms |
| 1 万行 | 18 ms | 24 ms | 43 ms |

- 解析だけを Worker に移しても、受け取った JSON をオブジェクトに戻す処理（1 万行で約 19 ms）は画面のスレッドに残る。今の TS の解析と変わらず、入力が止まらなくなる効果は無い。
- 一方で、解析結果を待つ間に図を操作すると、古い解析結果の位置でテキストを書き換えるおそれがある。これを防ぐには図の操作の作りを変える必要があり、モデル構築を Rust に移す alpha.4 でまとめて行うほうが手戻りが無い。
- 利用者のモデルの大半は数百行で、同期で呼んでも 2 ms 程度で済む。

## 結果

- 1 つのテストの集まりで、TS と Rust のどちらが仕様からずれたかがわかる。仕様のケースを足すほど、Rust の基準も厚くなる。
- パーサだけを先に差し替えるので、alpha.3 で壊れうる範囲が小さい。
- alpha.3 では、1 万行のような大きなモデルで、解析が今より 25 ms ほど遅くなる。alpha.4 で、解析とモデル構築をまとめて Worker に移して解消する。
- alpha.4 からは解析が非同期になり、大きなモデルでも入力が止まらない。その代わり、結果が届くまでの間、図は一つ前の解析結果のままになる。
- 段階 A の間は、式を読まない。式の中の参照の検査は、段階 B まで今と同じ程度にとどまる。
- テストの実行に wasm のビルドが要るため、`scripts/check.sh` が少し遅くなる。
