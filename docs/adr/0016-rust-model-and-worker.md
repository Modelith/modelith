# ADR-0016: モデル構築と図の操作を Rust に移し、コアを Worker で動かす

- 状態: 採用
- 日付: 2026-10-15

## 背景

alpha.3 で、解析を Rust のパーサ（wasm）に差し替えた（ADR-0015）。残る暫定の TS コアは次の 2 つである。

- **モデル構築**（`web/src/core/model.ts`・`views.ts`）：解析結果から、図の要素・関係・問題・フェーズ・保存された図を作る
- **図の操作**（`web/src/app/ops.ts`・`view-ops.ts` など）：要素の追加・名前の変更・削除・関係の追加・メッセージ・フェーズ・保存された図への出し入れ。
  15 ほどの操作が、解析結果のテキスト上の位置を使って、テキストを直接書き換えている

スプリント 4（`0.1.0-alpha.4`）では、これらを Rust に移し、コアを Web Worker で動かす（ADR-0003・ADR-0015 の改訂、Q-1）。
ADR-0015 の改訂で確かめたとおり、Worker に移すと、解析結果を待つ間に図を操作したとき、古い位置でテキストを書き換えるおそれがある。
図の操作をどう表すかを先に決めないと、Worker に移せない。

## 決定

### 1. 進める順序

壊れうる範囲を小さく保つため、同期のまま中身を Rust に移してから、最後に Worker に移す。

| 手順 | 内容 | 呼び方 |
| --- | --- | --- |
| A | モデル構築を Rust に移す | 同期（今と同じ） |
| B | 図の操作を Rust に移す | 同期 |
| C | コアを Worker に移す | 非同期 |
| D | 図に出した package を枠で描く（F-VIEW-9） | 非同期 |

手順ごとに PR を分け、それぞれで `scripts/check.sh`（e2e・UI テストを含む）を通す。暫定の TS コアは、比べるテストのために beta.1 まで残す（ADR-0009）。

### 2. モデル構築（手順 A）

- `modelith-core` に `model` 層を足す。ADR-0015 の `project` 層の結果から、暫定コアと同じ形の `Model` を作る。
  alpha.4 では暫定コアの振る舞いをそのまま移す。SysML v2 の意味（名前解決・継承など）に沿ったモデルへの作り直しは、0.1.0 の後に行う。
- wasm は、解析とモデル構築をまとめて返す（`analyze(text)`）。要素の参照は番号で渡し、TS の境界で今のオブジェクト（`nodeOf`・`byName` の Map、`phaseOf` の関数を含む）に戻す。
- `golden.test.ts`・`spec.test.ts` は、パーサとモデル構築の組（TS と Rust）の両方で動かす。
- どんな入力でも止まらないことを、解析とモデル構築を通して確かめる。乱数で作った入力を大量に流すテストを足す（ファジング。外部の道具は使わず、Rust の単体テストとして書く）。

### 3. 図の操作（手順 B）

- **図の操作は「意図」として表し、コアがテキストの編集を返す。** 意図は、要素を位置ではなく、キー（図の要素のキー・関係の ID）で指す。

  ```
  edit(text, { op: "rename", key: "Engine", name: "Motor" })
    → { edits: [{ start, end, text }, …], select?: "Motor", flash?: [start, end] }
  ```

- 返すテキストの編集は、今の TS と同じ、UTF-16 の位置の `{ start, end, text }` とする。
  プラグイン向けの `TextEdit`（plugin-sdk、行・列で表す）への変換は、プラグインがテキストを編集するようになったときに境界で行う（ADR-0004。今は作らない）。
- UI（ダイアログ・確認・トースト・配置）は TS に残す。コアは、テキストをどう変えるかだけを決める。
- 操作を 1 つずつ移す。それぞれ、Rust の単体テスト（テキストを入れて、編集後のテキストを比べる）を足し、今の e2e テストで画面からの振る舞いを確かめる。

### 4. Worker（手順 C）

- コアは Worker の中で、今のテキストと解析結果を持つ。UI とのやり取りは、LSP と同じ考え方にする（ADR-0003）。

  | UI → Worker | Worker → UI |
  | --- | --- |
  | `didChange { version, text }` | `analyzed { version, parse, model }` |
  | `edit { version, intent }` | `edited { version, edits, select?, flash? }` |

- テキストを変えるたびに版を 1 つ上げる。Worker は届いた順に処理するので、`edit` は、その直前に送ったテキストに対して計算される。
- UI は、返ってきた結果の版が今のテキストの版と同じときだけ使う。違えば捨てる。
  - 解析結果が古ければ、次の結果を待つ。図は 1 つ前の結果のまま。
  - 編集が古ければ、その操作は適用しない。テキストが変わったことを利用者に知らせる。
- 解析中も入力と図の操作は止まらない。操作した直後の結果（追加した要素を選ぶなど）は、`edited` と、その次の `analyzed` を待って画面に反映する。
- 計測の目安：1 万行のモデルで、画面のスレッドでかかる時間（結果を受け取ってオブジェクトに戻す）が 30 ms 以内。超えたら、差分だけを送るなどを検討する。

### 5. package の枠（手順 D）

F-VIEW-9 は、Rust のモデル構築で package を図の要素として扱えるようにしてから入れる（リリース計画どおり）。

## 結果

- 図の操作が位置ではなくキーで表されるので、解析を待つ間の操作でも、古い位置を書き換えない。
- コアの振る舞いが Rust に集まり、CLI・LSP・サーバ（ADR-0002）から同じ操作を使える。
- 手順 A・B の間は同期のままなので、壊れうる範囲は「中身の差し替え」に限られる。非同期にする影響は、手順 C に集める。
- 操作した直後の画面の反映が非同期になる。追加した要素が選ばれるまでに、解析 1 回分の遅れが出る。
- テストの組（TS と Rust）が増え、beta.1 で TS 側を消すまで、テストの時間が少し延びる。
