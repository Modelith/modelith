# ADR-0007: dev 統合ブランチとマイルストーン単位のリリース

- 状態: 採用（2026-10-15 改訂：GitHub の既定ブランチを `dev` にした）
- 日付: 2026-10-10

## 背景

当初は `main` だけを長期ブランチとするトランクベース開発を採用し、`main` へのマージはすべてメンテナの許可制とした。
しかし AI エージェントが作るトピックブランチは依存関係を持って積み上がりやすく、1 本ずつ許可を待つと作業が詰まる。
一方で、リリース済みの状態（`main`）には人間の確認を必ず挟みたい。

## 決定

- 統合ブランチ `dev` を設ける。トピックブランチは `dev` から作り `dev` に戻す。
  GitHub の既定ブランチは `dev` とする（2026-10-15 改訂。当初は `main` だった）。PR の向け先が自然に `dev` になり、手で起動するワークフローも `dev` の定義で動く。
  リリース済みの状態は、GitHub のリリースと Pages で見せる。PR の向け先の誤りは、引き続き CI で検出する。
- トピック → `dev` は Squash merge。CI がグリーンで未解決のレビューコメントがなければ、**AI エージェントが許可なしでマージしてよい**。
- `dev` → `main` は **マイルストーン（リリース）ごと**に、**メンテナの明示的な許可を得てから**マージコミットで行い、`main` にタグを打つ。
- 緊急修正のみ `fix/*` を `main` から作り `main` に入れる（許可制）。直後に `main` → `dev` をマージコミットで同期する。
- `release/*` ブランチは引き続き作らない。
- この権限はハーネスで強制する（`guard-merge.sh` がマージ先・マージ元・方式を見て許可／承認要求／拒否を決める。
  `guard-git.sh` が `main` / `dev` への直接 push をブロックする）。
- plugin-sdk など関連リポジトリも同じ運用とする。

詳細な手順と GitHub 側の設定は [branching-strategy.md](../development/branching-strategy.md) を参照。

## 結果

- エージェントは許可待ちなしで `dev` に統合を進められ、人間の確認はリリースの単位にまとまる。
- `dev` → `main` を Squash しないことで、`dev` と `main` の履歴が分岐しない。
- 長期ブランチが 2 本になるため、緊急修正後の `main` → `dev` 同期を怠らないこと。
