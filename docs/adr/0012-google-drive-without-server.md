# ADR-0012: クラウド保存は Google ドライブから始め、サーバを持たずにブラウザから直接つなぐ

- 状態: 保留（必要になったら着手する）
- 日付: 2026-10-13

> 2026-10-13 保留：クラウド保存は今の利用者に必要ではない（YAGNI）。一度入れたプロバイダの実装（modelith/modelith#20）は取り除いた。
> 着手するときは、この ADR の方式から始め、Git の履歴にある実装とテストを参考にする。

## 背景

利用者は、手元のファイルだけでなくクラウドのファイルも同じ操作で開いて保存したい（F-FILE-12）。
その先では、チームでモデルを共有し（段階 2）、いずれは Web サービスとして運営することも考えている（段階 3。[リリース計画](../development/release-plan.md)）。

一方で、今の Modelith には次の約束がある。

- サーバを持たない静的なファイルとして配信する（C-4、ADR-0003）
- 利用者のモデルを外部に送らない（C-2）

SysML のモデルは製品の設計情報で、利用者は自分たちの管理外に置くことに慎重である。
自前のアカウントとサーバを持てば、保存・認証・個人情報・障害対応のすべてを運営側が負うことになる。

## 決定

- **最初のクラウドは Google ドライブにする。** 共有フォルダがあるため、段階 2（チームで共有）にも同じ仕組みで進める。
- **サーバを持たない。** ブラウザから Google の API に直接つなぐ。モデルは利用者自身のドライブにだけ置き、Modelith の運営側は受け取らない。
- **認証は Google Identity Services のトークン方式（ポップアップ）を使う。**
  - アクセストークンはメモリにだけ置き、localStorage などに保存しない。期限が切れたら、利用者の操作で取り直す。
  - リフレッシュトークンは使わない（扱うにはサーバが要るため）。
  - OAuth クライアントの「承認済みの JavaScript 生成元」に配信元を登録し、リダイレクト URI は使わない。
- **権限は `drive.file` だけにする。** Modelith で開いた・作ったファイルにだけ触れ、ドライブ全体は読めない。
  - 既存のファイルは、Google のファイル選択画面（Google Picker）で利用者が選んだものだけを開く。
  - Google の審査が軽い権限で済む。
- **ADR-0010 のプロバイダとして足す。** `GoogleDriveProvider` を作り、次のインタフェースを実装する。
  - `Readable`・`Writable`・`FilePicker`・`SaveAsTarget`
  - 版（version）には、ドライブのファイルの `version`（更新のたびに増える番号）を使う
  - Drive API v3 の更新には条件付きの書き込みが無い。上書きの直前に版を読み直して比べ、変わっていれば `ConflictError` にする。読み直しから書き込みまでのわずかな間の競合は防げない
  - 認証は、このプロバイダの中に閉じる。ワークスペースと UI は変えない
- **Google の API は外から渡す。** Google のスクリプトを読み込む部分と、HTTP の呼び出しを、プロバイダに注入する。
  単体テストと e2e は偽の API で動かし、本物の Google は呼ばない。
- **Google のスクリプトは、利用者がドライブを使うときに初めて読み込む。** ドライブを使わない利用者は、これまでどおり配信元以外と通信しない。
- **C-2 の意味をはっきりさせる。** 利用者が選んだ保存先（手元のファイル、利用者自身のクラウド）に保存するのは「外部に送る」に当たらない、と要求仕様に書く。
- クライアント ID と API キーは、ページに埋め込む公開の値として扱う。代わりに、許可する配信元と API の利用元を Google Cloud 側で制限する（[手順](../development/google-cloud.md)）。

## 段階 2・3 への見通し

- **段階 2（チームで共有）:** ドライブの共有フォルダで、同じファイルをチームで開く。
  同時に編集したときは、ADR-0010 の版の比較（F-FILE-7）で競合を検出し、利用者に選ばせる。
  リアルタイムの同時編集はこの段階では扱わない。Git や GitHub での共有も、プロバイダとして並べて検討する。
- **段階 3（Web サービス）:** 自前のアカウントとサーバが必要になり、C-2・C-4 と ADR-0003 を見直すことになる。
  利用者の反応を見てから、改めて ADR で判断する。この ADR はその判断を先取りしない。

## 結果

- サーバと運用費を持たずに、クラウド保存とチームでの共有まで進められる。
- モデルは利用者のドライブにだけあり、運営側が設計情報を預からない。
- ドライブを使うには Google アカウントでのログインが要る。ログインの期限が切れたら、利用者が取り直す。
- Google Cloud のプロジェクト（OAuth クライアント・API キー・同意画面）を、メンテナが用意して管理する。
- 一般公開の前に、プライバシーポリシーとホームページを用意し、Google のブランド確認を受ける必要がある。
