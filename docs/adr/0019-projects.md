# ADR-0019: プロジェクト（フォルダ単位の作業の場と、チームで共有する設定）

- 状態: 採用
- 日付: 2026-10-17

## 背景

Modelith は「フォルダを開く」（F-FILE-1）で、開いたフォルダを作業の単位にしている。配置ファイル（ADR-0005）もそのフォルダの中に置く。
ただ、そのフォルダには名前も設定も無いので、次のことを置く場所が無い。

- プラグイン（ADR-0018）：チームの全員と CI が同じものを使いたい。モデルが使うプラグインが入っていないと、プラグインが配る定義（例：FMEA の項目の定義）が見つからず、問題一覧に誤りが出る
- チームでそろえたい設定：検査ルールの選び方、FMEA の評価の方式など。人によって違うと、同じモデルでも結果が変わる
- 文書へのリンクの起点：要素から `docs/spec.pdf` のようなファイルを指すとき、どのフォルダから見た場所かが決まらない
- 複数のファイルにまたがるモデル：どのファイルの集まりが 1 つのモデルかを決める単位が要る（今は 1 ファイルずつ解析している）

VS Code の「ワークスペース」が同じ役割を持つが、「フォルダを開く」と「ワークスペースファイル（複数のフォルダを束ねる）」が並び、設定も何段にも重なるため分かりにくい。
Modelith では、SysML v2 の構文を知らない人にも分かる形（ADR-0014）にする。

## 決定

### 1. 呼び名と単位

- 画面では「**プロジェクト**」と呼ぶ（「ワークスペース」は使わない）。
- **1 プロジェクト ＝ 1 フォルダ**。複数のフォルダを束ねる仕組みは作らない。
- プロジェクトの印は、フォルダの一番上に置く設定ファイル **`modelith.json`** とする。隠しフォルダには置かず、利用者と Git の差分で見えるようにする（`package.json` と同じ考え方）。
- Modelith が中身を管理するファイル（プラグインの本体など）は、`.modelith/` に置く。利用者が直接触る必要はない。

  ```
  my-project/
    modelith.json          ← プロジェクトの印と、チームで共有する設定
    model.sysml
    model.layout.json      ← 配置（ADR-0005、今までどおり）
    docs/engine-spec.pdf   ← リンクで指せる文書
    .modelith/
      plugins/<ID>/        ← プロジェクトに入れたプラグイン（ADR-0018）
  ```

### 2. 設定ファイル（`modelith.json`）

```json
{
  "name": "給水システム",
  "plugins": {
    "jp.modelith.fmea": { "version": "0.2.0", "enabled": true, "settings": { "rating": "rpn" } }
  }
}
```

- `name`：画面に出すプロジェクト名
- `plugins`：プロジェクトが使うプラグイン。版・有効かどうか・プラグインごとの設定（中身はプラグインが決め、ホストはそのまま渡す）
- 項目は互換を保って足していく。未知の項目は消さずに残し、問題一覧で知らせる（F-EDIT-8 と同じ考え方）
- 形は Rust の型として `modelith-core` に置き、JSON Schema を生成する。プラグインの設定の中身は plugin-sdk の契約の外（プラグインごとの自由な JSON）とする

### 3. 設定は 2 段だけ

| 段 | 置き場所 | 中身 |
| --- | --- | --- |
| このプロジェクトの設定 | `modelith.json` | 結果に効くもの（プラグイン・検査ルール・評価の方式など）。チームで共有し、CI も読む |
| 自分の設定 | ブラウザ | 見た目と操作の好み（配色・自動保存など）。自分だけ |

- **1 つの項目は、どちらか一方にだけ属する**。同じ項目が 2 段にあって上書きし合う形にはしない（VS Code の分かりにくさの元）。
- 画面の設定は、この 2 つを並べて見せる。

### 4. 画面

- 画面の上部に、今のプロジェクト名を出す。設定ファイルの無いフォルダでは、フォルダ名を出す。
- **設定ファイルの無いフォルダも、今までどおり開いて使える。** 「プロジェクトにする」を押したときに初めて `modelith.json` を作る。
  プラグインを「このプロジェクト」に入れるときは、作ってよいかを尋ねてから作る（C-6：利用者の操作なしにファイルを書かない）。
- フォルダを開けないブラウザ（F-FILE-10）や、1 つだけ開いたファイル・サンプルでは、プロジェクトは無い。そのことと、できないこと（プロジェクトに入れたプラグインなど）を画面に示す。

### 5. CLI

- `modelith check <フォルダ>` は、そのフォルダの `modelith.json` を読み、プロジェクトに入れたプラグインで検査する。画面と同じ結果になる（ADR-0018）。

### 6. 文書へのリンク（0.2.0 の候補）

- リンクは**テキストにメタデータとして書く**（ADR-0001）。ほかの SysML v2 ツールで開いても情報が残る。

  ```
  part engine : Engine {
      @DocumentLink { url = "docs/engine-spec.pdf"; title = "エンジン仕様書"; }
  }
  ```

- プロジェクトの中のファイルは、**プロジェクトのフォルダからの相対パス**で書く。Web の URL も書ける。
- 画面では、要素からリンクを開ける。プロジェクトの中の PDF や画像は、開いているフォルダから読む。
- プロジェクトの中のファイルへのリンク切れは、問題一覧に示す（検査ルールの 1 つ）。
- リンク先を勝手に読みに行かない（プレビューのための通信をしない。C-2）。開くのは、利用者が操作したときだけ。
- `DocumentLink` の定義は、Modelith が配るライブラリとして用意する。詳細は 0.2.0 の前に決める。

## 進める順序

| 時期 | 内容 |
| --- | --- |
| alpha.5 | `modelith.json`（名前とプラグイン）、画面のプロジェクト名、「プロジェクトにする」、CLI がプロジェクトを読む |
| 0.2.0 の候補 | 文書へのリンク、複数のファイルにまたがるモデル |

## 結果

- モデルと一緒に、使うプラグインとチームの設定を Git で持ち運べる。チームの全員と CI が同じ環境になる。
- モデルが使うプラグインが入っていないとき、何が足りないかを示せる（ADR-0018）。
- 設定ファイルの無いフォルダの使い方は変わらない。
- 設定の重なりを作らないので、「どの設定が効いているか」で迷わない。
