# ADR-0011: 要求仕様を 1 つの SysML v2 ファイルで管理する

- 状態: 採用
- 日付: 2026-10-12

## 背景

これまで要求は、モックの挙動（ゴールデン）・ADR・リリース計画の機能一覧に散らばっていた。
テストユーザーに使ってもらう段階に入り、何を約束していて、何が実装済みかを 1 か所で確かめられる必要がある。

## 決定

- 要求仕様の唯一の定義元（SSoT）を [`docs/reference/requirements.sysml`](../reference/requirements.sysml) とする。
  Markdown ではなく SysML v2 で書き、Modelith 自身で開いてトレーサビリティを確かめる（ドッグフーディング）。
- 構成は Modelith のフェーズに合わせる。
  - 利用者要求（`N-*`）→ システム要求（機能 `F-*`・品質 `Q-*`・制約 `C-*`）を `#derivation` で導出する
  - システム要求を満たす部品を `satisfy` で示す
  - 自動テストを `verification def` とし、`verify` で要求に結ぶ。**verify されている要求を「実装済み」とみなす**
- ID は一度振ったら変えない。廃止する要求は消さずに、doc の先頭に「廃止：」と書く。
- 振る舞いを変えるときは、実装より先にこのファイルを更新する（CLAUDE.md）。
- `web/src/requirements.test.ts` が、このファイルの構文・ID の一意性・導出と充足の抜けを検査する（ハーネスで強制）。
  verify の抜けは「未実装・未検証」の表示として許す。

## 結果

- 要求・設計・テストのつながりを、Modelith のトレーサビリティ図とトレースの抜けの一覧で確かめられる。
- GitHub 上ではただのテキストとして表示される。利用者向けの説明は `docs/` に別に書く（要求そのものは複製しない）。
- パーサの対応範囲の制約を受ける。書けない表現が出てきたら、パーサを直すか、このファイルの書き方を変える。
