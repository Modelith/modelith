# テスト原則

対象は実コード（Rust・TypeScript）とハーネス（シェルスクリプト・フック・Node スクリプト）のすべて。
**ISTQB の 7 原則、テストレベルの順序、テスト設計技法、AAA パターンは厳守事項**である。

## 1. ISTQB テストの 7 原則（厳守）

| # | 原則 | このリポジトリでの実践 |
| --- | --- | --- |
| 1 | テストは欠陥があることは示せるが、欠陥がないことは示せない | 「テストが通った」を「正しい」と言い換えない。報告では確認した範囲を明記する |
| 2 | 全数テストは不可能 | 同値分割と境界値分析でケースを絞り、リスクの高い所に厚くする |
| 3 | 早期テストで時間とコストを節約 | 実装と同時にテストを書く。仕様（ADR・ゴールデン）の段階で検証方法を決める |
| 4 | 欠陥は偏在する | 欠陥が見つかった箇所の周辺にテストを追加する。修正時は再発防止のテストを必ず足す |
| 5 | 殺虫剤のパラドックスに注意 | 同じテストを繰り返すだけで満足しない。欠陥・仕様変更のたびにケースを見直し、追加・更新する |
| 6 | テストは状況次第 | パーサは境界値と異常系、UI 同期は結合、ハーネスは終了コードと判定結果、と対象に合わせて技法を選ぶ |
| 7 | 「バグゼロ」の落とし穴 | 欠陥がないことより、要求（ADR・ユーザーの意図）を満たしているかを確かめる |

## 2. テストレベルと実施順序（厳守）

**単体 → 結合 → 統合 の順に実施する。** 前のレベルが失敗したら次へ進まない（`scripts/check.sh` がこの順で実行し、失敗した時点で止まる）。

| レベル | 対象 | 置き場所 |
| --- | --- | --- |
| 単体テスト | 1 つの関数・モジュールを I/O なしで | Rust: `#[cfg(test)] mod tests`、TS: `*.test.ts`、ハーネス: `tests/harness/unit/` |
| 結合テスト | モジュール・プロセスをつないだ動作（フックに JSON を入れる、一時的な Git リポジトリ、スタブ化した外部コマンド） | Rust: `crates/*/tests/`、ハーネス: `tests/harness/integration/` |
| 統合テスト | システム全体の通しの動作（`check.sh` の段階実行、wasm ビルド、仕様との一致、Web の E2E。将来は CLI も） | Web: `web/e2e/`（Playwright）、`tests/harness/system/`、CI |

## 3. テストケースの設計（厳守）

テストを書く前に、対象ごとに次の 4 つを洗い出し、テスト名またはコメントに反映する。

1. **同値分割**：入力を「同じ振る舞いをするはずの集合」に分け、各集合から代表値を 1 つ選ぶ。有効な集合と無効な集合の両方を作る。
2. **境界値分析**：各集合の境界（最小・最大・その ±1、空、0、末尾）を必ずテストする。
3. **正常系**：仕様どおりの入力で期待どおりの結果になること。
4. **異常系**：不正な入力・失敗する外部依存・欠けた設定で、期待どおりに失敗（エラー・終了コード・拒否）すること。

例（ブランチ名の検査）:

| 分類 | 同値クラス | 代表値 | 境界値 |
| --- | --- | --- | --- |
| 正常系 | 規約どおりの `<type>/<topic>` | `feat/kerml-parser` | topic 1 文字 `feat/a` |
| 正常系 | 保護ブランチ | `main`, `dev` | — |
| 異常系 | 未知の type | `feature/x` | — |
| 異常系 | 大文字を含む | `fix/Bad` | — |
| 異常系 | topic が空 | — | `feat/` |

## 4. AAA パターン（厳守）

すべてのテストは **Arrange（準備）→ Act（実行）→ Assert（検証）** の 3 区切りで書き、区切りをコメントで明示する。

```rust
#[test]
fn line_col_rejects_offset_past_end() {
    // Arrange（境界値: len + 1）
    let idx = LineIndex::new(TEXT);
    // Act
    let pos = idx.line_col(TEXT.len() + 1);
    // Assert
    assert_eq!(pos, None);
}
```

```bash
@test "policy_branch_name: 未知の type は拒否する（異常系）" {
  # Arrange
  load_policy
  # Act
  run policy_branch_name feature/x
  # Assert
  [ "$status" -eq 1 ]
}
```

- 1 つのテストで検証する振る舞いは 1 つ。Act は原則 1 行。
- 例外の送出を確かめるなど実行と検証が分けられない場合だけ `// Act & Assert` とまとめてよい。
- テスト名は「何が・どの条件で・どうなるか」を書く。
- テスト同士で状態を共有しない（順序に依存させない）。

## 5. ハーネスで強制する項目

`scripts/check.sh` が単体 → 結合 → 統合の順に実行し、失敗した段階で止める。
テスト設計（同値分割・境界値・正常系／異常系・AAA）と ISTQB の原則は指針として、下のチェックリストで自己レビューする。

## 6. チェックリスト

- [ ] 同値クラス（有効・無効）を洗い出し、各クラスの代表値をテストしたか
- [ ] 境界値（最小・最大・±1・空・末尾）をテストしたか
- [ ] 正常系と異常系の両方があるか
- [ ] すべてのテストが AAA の 3 区切りになっているか
- [ ] 単体 → 結合 → 統合の各レベルで必要なテストを置いたか
- [ ] 欠陥修正なら、その欠陥を再現するテストを先に書いたか（原則 4）
- [ ] 既存テストが今の仕様に合っているか見直したか（原則 5）
