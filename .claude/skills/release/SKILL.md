# リリース

手順の正本は [docs/development/releasing.md](../../../docs/development/releasing.md)。ここはエージェントが迷わないための要約と、リリースノートの書き方。

## 前提

- **リリースを始める前に、メンテナに進めてよいか確かめる。** 許可は版ごとに取り、前の版の許可を流用しない。
- エージェントにできるのは、下書きまで。タグの作成と公開は、メンテナが GitHub の画面で「Publish release」を押したときに行われる。
- alpha・beta は `dev` で出し、`main` にはマージしない。rc から先は releasing.md に従い、`main` へのマージは毎回メンテナの許可を取る。

## 手順（alpha・beta）

1. `dev` の CI がグリーンで、出したい変更がすべて `dev` に入っていることを確かめる。
2. `dev` から `chore/release-v<版>` を作り、`scripts/release-prepare.sh <版>` を実行する（版の書き換えと、ノートのひな形）。
3. `docs/releases/v<版>.md` の「（ここに書く）」を、下の「書き方」に従って埋める。
   前の版から出した PR（`git log v<前の版>..origin/dev --oneline`）を読み、利用者に見える変化を拾う。
4. `node web/tools/release-notes-cli.ts check <版>` と `scripts/check.sh` を通す。
5. PR `chore(release): v<版>` を `dev` に向けて出す。本文にはリリースノートの全文を入れる。CI グリーンで Squash merge する。
6. マージで「Release draft」ワークフローが動き、下書きができる。実行の結果（`actions_list` / `get_job_logs`）から、下書きのページのリンクを取る。
7. 下書きのリンクをメンテナに渡し、「Publish release」を押してもらう。下書きの `releases/tag/untagged-…` のリンクは直接開けないことがあるので、
   リリースの一覧（`https://github.com/modelith/modelith/releases`）と、編集画面（`releases/edit/untagged-…`）のリンクを渡す。
8. 公開されたら、Pages のワークフローが成功したことと、画面右上の「ヘルプ」に出る版を確かめる。
   alpha・beta は `/modelith/preview/` に、正式版（無ければ最新の rc）は `/modelith/` に出る（ADR-0020）。公開した版が出るはずの URL で確かめる。リリース計画（release-plan.md）のその行に「（公開済み）」を足す PR を出す。

下書きが作られなかったときは、ワークフローのログの理由（ノートが無い・版が違う・ブランチが違う）を直す。
手で作り直すときは、ワークフロー `release-draft.yml` を `ref: dev`、inputs `version`・`branch: dev` で起動する（`actions_run_trigger`）。
公開済みの版のノートを直すときも、同じく手で起動する（本文だけを差し替える）。メンテナに頼まれたときだけ行う。

## リリースノートの書き方

- **読み手は利用者。** SysML v2 の構文を知らない人にも分かる言葉で書く（ADR-0014、[画面の言葉の手引き](../../../docs/development/ui-writing.md)）。
  ADR・テスト・CI・内部の作りなど、開発者だけに関係することは書かない（それは PR とコミットに残っている）。
- **前の版のノート（`docs/releases/` の直前の版）を読んでから書き、語り口と粒度をそろえる。**
- 形（`check` で検査する）：
  1. `# Modelith <版>`
  2. この版で何が変わったかの要約を 1 段落（1〜2 文）
  3. 変更の種類ごとの節を、この順に 1 つ以上（当てはまる変更が無い節は消す）。どれも箇条書きで「- 項目の名前：何がどう変わったか」。文末に句点を付けない
     - `## 新しい機能`：今までできなかったことが、できるようになった
     - `## 改善`：今までもできたことが、速く・分かりやすく・使いやすくなった
     - `## 不具合の修正`：意図と違う振る舞いを直した。「〜していました。〜するようになりました」と、前の振る舞いと直った後の振る舞いを書く
     - `## その他`：上のどれにも当たらないが、利用者が知っておくべきこと
  4. `## <前の版> をお使いの方へ`（任意）：保存形式の変更や、前の版から使い方が変わる点。無ければ節ごと消す
  5. ご注意・商標・ライセンス（決まった部分。ひな形に入っているものを変えない。変えるときは `web/tools/release-notes.ts` の `FOOTER` を直す）
- 利用者に見える変化だけを、節の中で影響の大きい順に並べる。
- **前の版を使っていた人にとっての変化だけを書く。** この版の開発中に入って、公開前に直した問題は書かない（前の版の利用者は出会っていない）。
- 画面から使えない機能（テキストで書いたときだけ働くもの）は、その書き方を例で示す。画面からできるように読める書き方をしない。
